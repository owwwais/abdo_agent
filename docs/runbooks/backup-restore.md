# النسخ الاحتياطي والاسترجاع

يغطي مخطط `sales` (كل بيانات العمل والتدقيق) ومخطط `sales_graph` (حالة سير العمل الدائمة).

## نسخة

```bash
uv run python scripts/backup.py dump
```

يقرأ `DATABASE_URL` من `.env`، ويكتب `backups/sales-<التاريخ>.dump` بصيغة pg_dump المخصصة. المجلد مستثنى من git.

**الملف يحوي بيانات عملاء حقيقية:** خزنه مشفرًا (قرص مشفر أو أرشيف بكلمة مرور)، ولا ترفعه إلى تخزين عام، واحذف النسخ القديمة وفق سياسة الاحتفاظ لديكم.

لنسخ الإنتاج من جهازك:

```powershell
$env:DATABASE_URL="<رابط Session pooler>"; uv run python scripts/backup.py dump
```

## تحقق (اختبر الاسترجاع قبل أن تحتاجه)

```bash
uv run python scripts/backup.py verify backups/sales-20260922-120000.dump
```

ينشئ قاعدة مؤقتة على الخادم نفسه، ويسترجع فيها، ويطبع عدد صفوف الجداول الأساسية، ثم يحذفها. نسخة لم تُختبر ليست نسخة.

## استرجاع

```bash
uv run python scripts/backup.py restore backups/<الملف>.dump --target-url <رابط القاعدة الهدف> --yes
uv run alembic current
```

- القاعدة الهدف **يجب أن تكون فارغة** من مخطط `sales`؛ السكربت يرفض غير ذلك حتى لا يُكتب فوق بيانات قائمة.
- للتعافي من كارثة: أنشئ مشروع Supabase جديدًا، استرجع فيه، ثم حدّث `DATABASE_URL` في Render وأعد النشر. `DATA_HASH_KEY` و`SECRETS_ENCRYPTION_KEY` **يجب أن يبقيا كما كانا**، وإلا انكسرت مطابقة منع التواصل وتعذر فك مفاتيح الإعدادات.
- بعد الاسترجاع راجع: عدد الفرص، وآخر رسالة صادرة، وأن أوامر الإرسال المعلقة لم تعد صالحة (الاعتمادات المنتهية تُنظَّف تلقائيًا في مهمة التنظيف اليومية).

## إصدار الأدوات

`pg_dump` و`pg_restore` يجب ألا يقل إصدارهما الرئيسي عن إصدار الخادم. السكربت يبحث في `PATH` أولًا ثم في نسخة pgserver المحلية (16)، ويتوقف برسالة واضحة إن كانت أقدم من خادم Supabase. ثبّت أدوات عميل PostgreSQL المطابقة عند الحاجة.

## الدورية المقترحة

- نسخة أسبوعية يدوية على الأقل، ونسخة قبل أي ترحيل كبير أو تغيير في الإعدادات.
- `verify` شهريًا على آخر نسخة.
- خطط Supabase المدفوعة توفر نسخًا يومية تلقائية؛ اعتبرها طبقة إضافية لا بديلًا عن نسخة بيدك تعرف كيف تسترجعها.
